How it plays

1

Launch a tank

Tap a colour tank from a supply lane or a waiting slot. It joins the belt if the belt has room. The x/5 counter shows the belt's capacity.

2

Ride the belt

The belt loops around all four sides of the picture. At each stop, the tank fires inward at the first pixel in that row or column, but only if that pixel matches its colour.

3

Park or run dry

A tank leaves when its ammo runs out. If it finishes a full lap with ammo left, it parks in one of 5 waiting slots so you can launch it again later.

4

Clear the picture

Destroy every pixel to win. You lose if a tank needs a slot while all five are full, or if none of the parked colours can reach any pixel.

Engineering highlights

I built the game to stay smooth on mobile at any board size. Every claim below is checked by an automated test.

GPU-instanced board

The whole pixel board is drawn with Graphics.RenderMeshInstanced, with one cube instance per pixel and a custom instanced colour shader. A 64×64 picture is a few draw calls, not 4,096 GameObjects.

Zero-allocation gameplay

A custom ObjectPool, a time-sliced TimeSlicedQueue and pre-sized buffers keep the hot path free of allocations. A PlayMode test reads the profiler and requires 0 B GC alloc in each of 240 frames while the largest level is busy.

O(1) four-sided fronts

PixelGridModel keeps a front pointer for every row and column on all four sides, plus a per-colour counter. Finding a tank's target and checking whether a colour can still hit anything are both constant time.

Fixed-tick belt simulation

The belt is a loop of 2W + 2H discrete positions. A lap always takes 4 s, so the tick is 4 / L seconds, and the controller catches up with up to 16 ticks per frame. The views interpolate between ticks so motion stays smooth.

Data-driven levels

Levels are saved as run-length-encoded binary or JSON and validated on load. A tank generator orders ammo to match how the belt sweeps the board, and an editor Level Baker turns any texture into a pixel level through colour quantization and tank generation.

Generated scenes

Editor builders generate the Loading, Menu and Game scenes, the HUD and the popups from code. The scenes can be rebuilt any time without manual scene edits.

Architecture

The code is split into layers by assembly definitions. The rules are plain C# with no MonoBehaviour, so they can be tested without a running game.

Testing

  • 126 EditMode tests cover the grid model, belt rules, shooting, serialization, level tools, progress and settings.
  • 15 PlayMode tests drive the real Game scene: tap-to-launch, overflow and the lose latch, auto-play to a win on the first and largest levels, cycling through all six levels, retry, and level-load time under 1 s.
  • Stress test: auto-plays a 5,000-cell board, with an average belt tick under 2 ms.
  • Frame budget: on the 64×64 level, the main thread stays under 16.6 ms with 0 B GC per frame.
